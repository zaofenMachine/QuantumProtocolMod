# 第二十阶段：原生手牌数量与满手牌暂存

日期：2026-09-13（Asia/Shanghai）。版本：v0.21.0。

## 问题与方案

此前固定牌序只安排了开局抽牌的内容，仍依赖原生开局抽五张恰好产生可用暂存布局。目标是六、七张手牌，或者所有牌都在牌库时，卡牌总集合正确也无法直接进入旧恢复计划。

本阶段增加独立的纯手牌计划和游戏线程执行阶段。先验证“当前原生牌库 + 逆序开局手牌”等于按保存内容构造的固定序列；再将启动手牌逆序通过 DEFAULT MoveCard 放回牌库，按保存手牌顺序逐张移回 HAND。每一步都验证具体运行时对象、原生区域顺序和公开 `getHandLimit()`，没有修改牌区容器或 `startingHandSize`。本机公开手牌上限为七张。

场地恢复需要临时把一张 DECK 卡放进 HAND。如果保存时已经满手牌，先补到上限减一张，暂时把最后一张目标手牌算作保留在牌库的卡，恢复墓地和场地后再补回。执行视图的临时目标不会覆盖保存文件，异常时也恢复完整目标用于报告和 Route C 回退。

普通同名水果会使最后保留的副本与场地计划重新分配对象。场地验证通过后，最后一步重新绑定仍留在牌库末尾的正确副本，不使用场地计划之前保存的旧目标指针。旧 schema 1 继续使用原启动路径；特殊卡跨手/场/墓的同身份情况在手牌规划前拒绝。

报告新增 `playerHandStagingStatus`、`playerHandStagingCompletedMoves`、`playerHandLimit` 和 `playerHandCardDeferredForField`。最终仍需通过全部玩家补充与持续稳定性验证。

## 样本与验证

离线测试覆盖七张满手牌的逐步容量限制、重复身份顺序、将最后一张留到场地完成后、同名副本重新分配、全牌组在 DECK、错误原生顺序、超容量、旧格式和特殊卡重叠拒绝。构建与 CTest 通过。

开发夹具增加两个仅在显式开发构建中存在的操作：`Ctrl+Shift+F3` 将手牌逆序放回牌库；`Ctrl+Shift+F4` 按牌库下一张顺序补到公开手牌上限。原 `F10` 仍把手牌移至墓地。夹具只调用已验证的原生位置迁移，保存前另行导出库存确认完成；正式安装默认拒绝两代夹具标记。

六种新样本均从第十七阶段的八张牌合法检查点出发，经开发夹具、普通出牌、行执行和手牌重排生成，没有编辑检查点负载或卡牌数量。因此它们是原生状态夹具样本，不能称为全由普通游戏操作产生。新进程、正式无夹具 DLL 下，七张手牌加场地且最后一张与场地苹果同名的重点样本已通过完整实例、原生顺序、单卡状态及位置比较。

最终正式构建完成十轮 requested 恢复：六种新布局，空手牌场地、场地与墓地混合、全墓地回归，以及旧 schema 1 场地回归。九份独立库存比较的所有已采集玩家项一致。混合样本恢复后实际点击抽牌，原牌库末尾的春进入手牌末尾，基础倒计时回到 5。

纯七张手牌的稳定性窗口内主动重排后，报告 `223710-050` 检测到 deck/hand drift，随后 `223720-472` 完成 semantic-fallback。一轮场地组合拖动未实际改变原生顺序，保留为未生效输入记录，不计作负向验收。完整报告编号以证据目录 `validation-summary.json` 为准。敌人的当前运行状态仍不参与精确恢复承诺。

证据目录：`QuantumProtoclMod.runtime-evidence/20260913-player-hand-capacity`。测试脚本及逐例库存、比较结果保存在目录中。原检查点单独保存在 `checkpoint-before`。
