# 第十六阶段：玩家场地与墓地共存

日期：2026-09-13（Asia/Shanghai）。版本：v0.17.0。

## 当前方向

按用户决定，暂时搁置“重编程重开”，集中推进“小关重开 + 玩家精确恢复”。敌人继续由保存小关的原生流程生成；敌人精确状态和路线 B 的验收另行安排。当前不进行大规模重构，只把本次必需的玩家搬牌计划从 Mod 执行代码中分离。

## 本次实现

v0.16.0 的场地补充已经保存墓地数组，但运行时拒绝非空墓地。v0.17.0 沿用这个 schema 1 文件，将墓地和场地交给同一个计划与恢复事务：

1. 原生固定牌序启动后，校验保存牌库、手牌的相对顺序与全部卡牌身份、升级和数量。
2. `PlayerRestorePlan` 先保留应留在牌库、手牌的副本，再为墓地和每个场格分配不同的原生对象。计划不持有 UObject，也不执行写入。
3. 按保存墓地顺序逐张执行原生 `DEFAULT` MoveCard，逐次核验对象位置与墓地完整前缀。先搬墓地也能释放起始手牌中的暂存空间。
4. 继续现有的场地恢复：优先放置起始手牌里的目标，再从牌库移到手牌并原生出牌；临时抑制入场效果，落位后恢复效果数组、生命及攻击状态。
5. 严格比较牌库、手牌、墓地完整 Getter 文本，核验场格、生命、攻击状态与空 PENDING；回合、充能和其他请求层通过同一三秒终验窗口后才报告成功。

任何写后失败仍重新加载一次纯 Route C。场地报告增加 `exactPlayerFieldTrashTargetCount` 和 `exactPlayerFieldTrashCompletedCount`；场地补充覆盖墓地时，不同时启用独立的墓地补充。

## 保留的边界

- 场地卡仍限 `naturalApple`、`naturalLemon`、`naturalSpring`，当前生命为正且不超过原生基础生命；PENDING 为空，卡牌总集合与活动牌组相符。
- 保存牌库、手牌和场地均须非空。五张原生起始手牌中，必须有至少一个可搬往墓地或场地的目标，保证场地暂存有空位。
- 手、场、墓三个目的牌区不能共享“标签 + 升级”身份。同一个目的牌区中的多个副本可以分配；牌库内必须保留的副本先占位，避免误搬。
- 实机新增样本覆盖两张场地苹果和一张墓地“春”。多张墓地目标的选择有离线测试，更多真实墓地组合仍待验证。
- 当前排序 Getter 相等不代表手牌在屏幕上的左右排列相同。本阶段截图中，保存时“重编程、樱桃、樱桃”，恢复后为“樱桃、樱桃、重编程”；独立状态比较使用排序 Getter，因此不能覆盖这一视觉顺序差异。
- 墓地单卡动态效果、任意卡组、满充能和复杂玩家计数器仍不作完整精确承诺。
