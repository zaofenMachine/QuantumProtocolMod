# 第三阶段：C++ 只读战斗状态导出

## 目标

验证 UE4SS C++ Mod 能否绕过 Lua 对大型返回结构的封送崩溃，并取得两条检查点路线共用的状态：玩家牌组与缓存区、各牌区卡牌实例、敌方卡牌、精确场上位置、效果显示状态和计数器。

本阶段只读，不执行任何恢复或游戏状态修改。

## 运行结果

### v0.1 / schema 1

- UE4SS 3.0.1 正常加载 C++ DLL。
- 首份报告包含 23 个相关对象，读取到生命 `9/9`、战斗状态 `OPEN` 和 Spawner 波次字段，游戏未崩溃。
- 热键原为 `Ctrl+F11`；游戏自身也处理 `F11` 并切换窗口模式，因此后续改为 `Ctrl+F1`。

### v0.2 / schema 2

- 通过反射安全调用零参数 getter，并使用 `FProperty::ExportTextItem` 导出返回值。
- 报告包含 33 个对象，游戏未崩溃。
- `GI_Quantum_C:getCurrentDeckRun()` 返回完整 `FGameDeckRun`，包括牌组标识、9 张卡的构成与数量、升级字段和 loot sets。
- `getActiveDecklistInstances()` 返回完整卡牌实例列表；`getActiveStorage()` 在本次空缓存区场景中返回空值。
- 牌库、手牌、墓地、玩家场上、缓存区、双方待处理区均可通过 `getCardInstanceListSorted()` 读取。
- 每张活动卡都可取得标签、稳定 GUID、当前位置、当前生命、当前回合计数和 `FCardInfoInstance`。
- 本次报告中的 9 张玩家牌可以全部归入具体牌区，没有丢失或重复。

这证明 Lua 的大型 `Decklist` 崩溃不是底层数据不可读；C++ 路径能够稳定导出紧凑的玩家运行牌组。

### v0.3 / schema 3

- 报告包含 99 个对象，游戏未崩溃。
- 成功读取全部 20 个场上槽位：玩家/敌人、前排/后排、索引 0–4。
- 卡牌的 `CardPlacementComponent:getPlacedFieldSlot()` 可以与槽位的 `getPlacementInfo()` 精确关联。
- 本次敌人 `enemyCacheRandom` 被定位为敌方前排索引 2，当前生命 3、回合计数 7。
- 成功关联 13 个 `BP_CardEffectDisplay_C` 与对应的 `UMG_CardEffectDisplay_C`，取得效果类型、动作状态和激活阻塞条件。
- 上述敌人关联到两个效果显示状态：`IGNITION/NONE`，以及 `INIT/COMPLETE` 且带 `NOT_IN_RIGHT_LOCATION` 阻塞条件。
- 每张活动卡都关联到通用和特殊计数器对象；`getCurrentCounters()` 安全返回。本次 20 个计数器读数恰好均为 0。

## 已证明与尚未证明

已证明：

- C++ 反射读取路径在三次版本测试中稳定，不需要硬编码内存偏移。
- 玩家完整牌组/缓存区、各牌区实例、敌人身份、生命、回合计数和精确槽位都存在可读取路径。
- 卡牌到效果显示、计数器和槽位的对象引用可以构成完整关联图。

尚未证明：

- 效果显示 Actor/Widget 是否就是权威效果状态。当前数据足以描述 UI 和动作状态，但不能据此断言可以精确写回效果执行器内部状态。
- 非零通用/特殊计数器尚未实测。
- `ExportTextItem` 当前产生 UE 文本格式，尚未转换为稳定的结构化检查点 JSON。
- 尚未验证从菜单重新进入保存时战斗、创建敌人并安全写回状态的顺序。
- 特殊关卡的 Spawner 子类、Boss/教程辅助 Actor 可能还有必须保存的私有状态。

## 阶段结论

“重编程锚点”路线的读取侧已经从推测提升为基本可行：玩家牌组与缓存区可紧凑保存，敌方卡牌的核心实例状态和精确布局可枚举。当前最大风险已从“能否读取”转移到“哪些状态是权威状态、怎样按安全顺序重建并写回”。

下一阶段应继续保持只读优先：补齐非零计数器与特殊敌人/Spawner 样本，梳理创建卡牌和进入关卡的原生调用链，然后才设计可回滚的单敌人恢复实验。
