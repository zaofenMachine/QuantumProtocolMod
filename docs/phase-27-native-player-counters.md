# 第二十七阶段：玩家计数器原生观测

日期：2026-09-13（Asia/Shanghai）。版本：v0.28.0。

## 状态来源

显示组件的 `getCurrentCounters` 仅读取组件自身 `+0x23C` 缓存。普通计数器的结算来源是卡牌原生状态 `+0x128`，纯 getter 为 `E26140`，多个卡牌效果直接读取它。特殊计数器存储在 `+0x1D8` 的 `TMap<FName,int32>` 中，稀疏条目步长为 20 字节，标签位于 0，数量位于 8。`E319D0` 按标签查询，`E31AF0` 求和供显示使用。

库存新增 `nativeCounters:*`。读取前验证 EXE、函数签名、活动世界、CardEngine 所有权及稀疏布局；逐标签导出特殊计数器，包括零值条目，以排序后的 JSON 字符串保存观测。手工计算的普通数量和特殊总量与纯原生 getter 对照，显示缓存仅做附加交叉观测。现有攻击与生命恢复路径不增加计数器写入。

比较工具新增独立 `playerNativeCountersAvailable` 和 `playerNativeCountersEqual`，按卡牌身份、牌区、场格、普通数量以及完整特殊标签表比较。缺少新观测时为未知，不推断为零。既有玩家状态、攻击和生命检查保持原覆盖范围。

## 原生动作样本

通过受限开发夹具向唯一场上苹果排入原生计数器动作：

- 普通计数器从 0 加到 3，再添加 3、上限 4，结果为 4；随后减去 10，结果归零。原生动作 `E0E710` 入队，`E3F8B0` 执行，正向添加受指定上限约束，最终数量不低于零。
- 特殊计数器标签 A 为 2、B 为 3；再调整为 A 为 3、B 为 2。原生总量与显示均保持 5，旧玩家状态、攻击与生命比较全部相等，只有新的逐标签计数器比较发现差异。库存分别为 `014759-350`、`014826-004`（日期 20260913）。
- A 从 3 减到 0 后条目仍在，再减 1 后 A 为 -1、B 为 2，总量为 1。`E0F100` 入队、`E3FD70` 执行的特殊计数器添加没有普通计数器的归零处理。恢复格式必须保留零值和负值条目。

这些样本是在同一张原生卡上经游戏动作形成，并分别等待结算后导出。夹具仅存在于开发构建，不直接覆盖原生计数器存储。

## 当前缺口与下一项

保存 A=2、B=3 的场地后，现有 schema 4 恢复仍只覆盖位置、攻击与生命，计数器回到零。恢复报告 `exactPlayerFieldStatus=verified-position-health`、攻击与生命比较通过，旧玩家卡牌状态和新增计数器比较都能识别计数器丢失。这是下一阶段要补齐的明确缺口。

本阶段加入计数器自比较、同总量不同标签的真实样本比较，以及缺少观测字段的未知状态测试；报告副本只用于比较测试，没有作为游戏存档。正式构建回归与证据见 `QuantumProtoclMod.runtime-evidence/20260913-player-counter-observation/validation-summary.json`。

正式构建关闭开发夹具，满手牌场地的新进程比较无差异，全 8 张墓地牌的状态比较与计数器观测通过，原始 schema 1 检查点恢复成功。DLL SHA-256：`1FA1B0BCE9EE339F920F1AF33C30947DED3F5ADD2D405D12F498B9C441297252`。

下一项为 FIELD 加入原生计数器恢复，包含零值和负值特殊条目；非零独立生命调整、LEVEL 及额外生成卡仍在后续范围。重编程重开和敌人精确恢复继续搁置。
