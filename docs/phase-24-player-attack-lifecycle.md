# 第二十四阶段：攻击修正顺序与生命周期

日期：2026-09-13（Asia/Shanghai）。版本：v0.25.0。

## 正负修正重放顺序

原生添加修正后会调用 `E56EC0` 调整过低的攻击值。该函数会修改负修正的 Amount，使结果不能低于零，因此恢复顺序会影响最终修正表。

真实原生动作样本为基础攻击 2、`zQuantumPositive` +3、`aQuantumNegative` -4，当前攻击 1。schema 3 规范序列按标签将负修正排在前面。旧恢复先添加 -4 时，原生下限调整破坏了需要恢复的负修正；实机请求以攻击校验失败结束，恰好一次普通 Route C 回退成功。

v0.25.0 保持检查点 schema 3 与标签排序不变，将原生重放次序改为非负修正优先、负修正在后，同组保持确定顺序。每步预期状态仍按标签规范化后与原生观测比较。相同检查点在修正后恢复到攻击 1，全部玩家比较项一致。失败报告增加卡牌索引及预期／实际修正记录，便于定位后续问题。

纯逻辑测试重现“逐步归零会令旧顺序得到 3，而正确顺序得到 1”的反例，并验证混合符号、多条修正和空修正表的次序。

## 独立衰减、归零与上限

本轮继续使用原生动作开发夹具构造样本，没有编辑检查点载荷。独立 DECAY +3 在三个普通回合依次变为 +2、+1，再移除；同一运行时苹果的攻击依次为 5、4、3、2，卡面与原生值一致。相关库存：`002037-369`、`002124-858`、`002151-562`、`002216-407`（日期均为 20260913）。

静态路径 `E40070 → E15850` 与实机一致：ONE_ATTACK 删除相应条目；DECAY 先将 Amount 减一，减至非正时移除，再调用原生攻击调整函数。本阶段不据此扩展到敌人状态恢复。

归零样本在 +3、-4 之上再添加 -2，原生表将负修正调整为 -5，保存攻击恰好为 0。上限样本两次添加同一 Tag 的 +2、limit=3，修正最终为 +3、limit=3，攻击为 5。以上均保存实际归一化后的 Amount，而不是重复原始增量。

正式构建分别复测正负共存、攻击归零、上限和剩余衰减检查点。验收包括牌区顺序、完整玩家卡牌状态和独立原生攻击统计，具体结果与恢复后衰减记录见运行证据清单。

恢复剩余 +1 衰减的两张苹果场地后，正常使用另一张苹果推进一个回合，同一运行时目标的修正删除、攻击从 3 回到 2。对应正式构建库存为 `002847-048` 与 `002857-886`。

构建与两个 CTest 目标通过。正式 DLL SHA-256：`83B9E164A9388B0BD31A463C0BCCDA00ED54DC431BDB0F47CD03B2A615E850B3`。证据位于 `QuantumProtoclMod.runtime-evidence/20260913-player-attack-lifecycle`，最终验收以 `validation-summary.json` 为准。开发用 Home、End、PageUp 组合热键只存在于显式开启夹具的 DLL 中，正式构建关闭。
