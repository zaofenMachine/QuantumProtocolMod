# 第二十八阶段：玩家场地计数器恢复

日期：2026-09-13（Asia/Shanghai）。版本：v0.29.0。

## 保存与恢复

FIELD schema 5 新增 `playerFieldCounterStates`，与场地卡牌及位置记录逐项对齐，并纳入补充文件校验和。每张卡保存普通计数和完整特殊标签表，格式为 `generic|tag,count|tag,count`，卡间使用分号。显式零值标签和不存在的标签保持区别，特殊计数允许负值及负总量。旧 schema 1—4 的校验和不变，报告明确给出 `exactPlayerFieldCounterStatus=legacy-unavailable`。

恢复先完成位置、攻击修正、生命修正及当前生命，再通过游戏原生动作队列重建计数器。普通计数使用 `E0E710`，特殊计数使用 `E0F100`；FName 通过反射参数构造，未调用视觉事件冒充状态恢复。每次调用验证游戏线程、活动世界、卡牌原生身份、玩家场地归属、EXE 与函数签名，并按原生 ABI 保留目标引用。

重建前要求新卡普通计数为零、特殊表为空。特殊标签非负值先入队，负值随后入队；零值也实际调用添加动作，以创建原生零值条目。每次动作只允许观察到入队前或预期的新状态，验证完成后才继续下一步。最终观察窗口反复校验完整标签表；外部变化触发一次纯 Route C 回退。

原生计数器动作按数量创建或移除显示对象，因此恢复暂定普通计数 0—256、特殊正值总和不超过 256、负值总和不低于 -256、最多 32 个安全标签。超出范围拒绝精确层，不截断数据。计数器标签表与属性修正表独立，同名标签可跨表存在。

## 实机证据

样本通过受限开发夹具调用原生动作形成，库存另行采集。保存文件未手工改写。

- 普通计数 3 恢复后，再加 3 且指定上限 4 得到 4，随后减 10 归零；恢复后的卡仍遵循原生行为。
- A=2、B=3 的完整标签表恢复成功；A=0、B=3 的零值条目恢复成功，证明原生添加零值会建立条目。
- A=-1、B=3 和 A=-1、B=-1 均恢复成功。后者总量 -2，原生读数、显示缓存与实机卡面一致。
- 同一卡同时具有攻击 +3、生命 +3、普通计数 3、特殊 A=2/B=3，恢复后逐项相等。
- 两张同名苹果，一张具有上述全部状态、另一张保持默认，正式构建的新进程恢复逐卡匹配。恢复不会因同名身份而混用动态状态。
- 最终观察窗口内将 A=2/B=3 改为 A=3/B=2，保持特殊总量 5。报告 `022747-471` 捕获标签分配变化，计数器状态为 `failed`，攻击、生命仍为已验证；`022757-613` 完成唯一一次语义回退。

正式构建关闭开发夹具，七组回归覆盖双同名牌组合、单卡全部补充、负总量、零值标签、普通计数，以及旧 schema 4 和 schema 2 满手牌样本。玩家牌序、身份、位置、生命、攻击与计数器比较全部通过；敌人状态仍可能不同，不属于本路线的精确承诺。原始 schema 1 检查点也恢复成功并保留。四个 CTest 目标全部通过。

证据目录为 `QuantumProtoclMod.runtime-evidence/20260913-player-field-counters`，包含采样、逐轮比较、干扰时序、DLL、源码、构建日志及 `validation-summary.json`。正式 DLL SHA-256：`BC14CE59348D533F28864FB327FEF4D9141B37C58011519E4BD203E246071B97`。
