# 恢复路线与成本取舍

## 结论摘要

2026-08-31 决定先闭环路线 C：普通地牢小关的语义重开。路线 C 利用游戏已有的关卡重载、波次生成和玩家牌组加载流程，只恢复能稳定表达的关卡上下文、牌组/缓存、波次和生命；它明确不承诺保存画面的精确复原。

这不是在 A/B 中提前认输，而是建立一个能跨进程、能拒绝不兼容状态、能产生验证报告的完整恢复骨架。A/B 的精确状态工作在 C 真实验收成功前冻结，避免继续积累私有字段而没有可用恢复入口。

## 决策记录：路线 C

首版数据流为：

1. 在普通 `DUNGEON` 的稳定 `OPEN` 波次保存角色、关卡、活动牌组、缓存区、运行摘要、生命、波次和 Spawner 身份。
2. 读取前校验 schema、负载校验和、2 MiB 上限、完整游戏 EXE SHA-256、模式和普通 Spawner 尺寸门。
3. 把关卡与牌组语义导入 `QuantumGameInstance`，调用 `reloadBattleArea()`。
4. 在新战斗第一次调用 `spawnWaveIndex` 前把参数重定向到保存波次。
5. 等待稳定 `OPEN`，暂停动作队列，调用 `resetPlayerBoard()` 和 `LoadPlayerCardsStart()`，恢复生命，再恢复动作队列。
6. 验证新 Spawner 实例、波次、生命、活动牌组和缓存区，写入 passed/failed 报告。

首版只允许无额外状态的普通 Spawner；无限模式、地牢事件、教程过滤器、Boss 监视器和特殊 Spawner 全部拒绝。路线 C 因此不能外推为“所有关卡已支持”。

真实验收成功必须同时满足：保存文件跨重启存在；读取进入同一普通小关；敌人按保存波次原生生成；牌组/缓存与保存数据一致；生命一致；可继续正常出牌和过关；报告为 `passed`；连续至少三轮不崩溃。任何一项失败都保留在 C 路线修复，不转入精确恢复。

## 冻结路线的比较依据

| 方面 | 小关开头检查点 | “重编程”后检查点 |
| --- | --- | --- |
| 玩家牌区 | 最难：需要精确还原手牌、场上、墓地、牌库等 | 可走原生重编程语义；`GameDeckRun` 已提供完整卡组与缓存区的紧凑表示 |
| 敌人 | 若锚点是真正的小关初始状态，可优先走原生生成 | 最难：必须精确还原保存时所有敌人实例与效果 |
| 随机性 | 精确牌序可能要求保存顺序或 RNG | 明确允许重新洗牌并抽五张 |
| 锚点频率 | 每小关自动产生，规则直观 | 只有使用并完成“重编程”后才产生 |
| 特殊内容 | 需验证小关开始事件在所有模式下一致 | 需验证极少数不带“重编程”的卡组如何处理 |

CXX SDK 又揭示了两条路线共同的底层障碍：`AInGameCard` 虽然可以读取标识、位置、当前生命和回合计数，但没有公开完整的权威状态 setter；动态效果和临时属性修改也没有完整集合 getter。小关路线在玩家卡牌上遇到这个问题，重编程路线在敌方卡牌上遇到这个问题。

此外，重编程路线还必须处理关卡专用状态。部分 Spawner 子类、无限模式、教程过滤器和 Boss 监视器拥有独立字段，不能用“敌人列表 + 波次索引”概括。因此目前的判断是：重编程路线的玩家侧明显更简单，但其敌人/关卡侧通用性风险高于此前估计。详见 [sdk-analysis.md](sdk-analysis.md)。

## 共同工程量

无论选哪条路线，都需要：

1. 稳定识别流程、关卡、小关和战斗对象生命周期。
2. 定义带版本号的检查点格式，并以临时文件加替换方式原子写盘。
3. 从主菜单或死亡流程重新进入正确战斗，而不是只修改当前内存对象。
4. 在恢复过程中暂停或隔离动作队列、生成器和胜负判定。
5. 恢复玩家生命、非卡牌资源、关卡计数器和 UI/输入状态。
6. 检测游戏更新造成的数据结构不兼容，并安全拒绝载入。
7. 建立可重复的状态签名和对比测试，证明恢复前后满足所选语义。

## 为什么 Lua 原型不适合作为最终恢复层

Lua 适合对象盘点、无参函数试验和快速验证，但当前 UE4SS 3.0.1 在调用返回大型 `Decklist` 结构的 `GI_Quantum_C:getActiveDecklist()` 时发生原生访问冲突。完整恢复还需要控制对象生命周期、拦截胜负判定并安全传递复杂结构，这些工作更适合 UE4SS C++ Mod。

因此建议正式实现使用 C++，Lua 探针继续只承担低风险、可丢弃的调查任务。

## 建议的分阶段决策门

### 基础阶段：两条路线共用

- 配置可编译的 UE4SS C++ Mod 工程并生成/整理本游戏 SDK。
- 建立只读对象枚举器，为玩家牌区、缓存区、敌人、关卡控制器生成稳定的 JSON 状态报告。
- 建立检查点文件版本、原子写入、校验和兼容性拒绝机制。
- 验证能从菜单重新进入指定流程和关卡，但暂不修改卡牌对象。

完成这一阶段后，才能用真实字段数量比较两条路线，而不是只凭 API 名称估算。

### 路线 A 验证门

- 选一个普通小关，证明玩家手牌、牌库、缓存、场上和墓地能逐项重建。
- 对升级、位置、生命、计数器和持续效果做状态签名比较。
- 证明动态效果和临时属性修改写入的是权威战斗状态，而不只是卡面 UI。
- 若实例身份或隐藏效果无法安全构造，则重新评估“精确”的定义。

### 路线 B 验证门

- 先验证跨进程读取和应用 `GameDeckRun.deck`、`GameDeckRun.storage` 后，卡牌标识、数量及升级等级完全一致。
- 只读完整记录一个重编程锚点的敌方场上、待处理区、墓地和控制器状态。
- 盘点实际 Spawner 子类、无限模式和关卡辅助 Actor；首版若排除特殊关卡，必须显式拒绝建立检查点。
- 在全新进入的战斗中重建敌方对象，期间抑制小关完成和自动生成。
- 对生命、位置、计数器、效果和后续敌人行为做状态签名比较。

当前生命和回合计数已分别通过跨帧私有写入、公开 getter 与 UI 同步验证，降低了两条路线共有的核心数值恢复风险。位置、通用/特殊计数器、持续效果、临时属性修改和对象创建后的行为一致性仍未闭合。

## 已排除的实现方式

在现有战斗中直接调用 `clearEnemyBoard()` 再调用 `spawnWaveIndex(savedWave)` 不可用。实测清掉最后一个敌人后，游戏先执行小关完成逻辑并进入下一小关；即使随后生成旧波次，也已破坏流程状态。恢复应从全新战斗上下文重建，或由原生层在恢复事务期间明确抑制过关判定。
