# 第二十六阶段：玩家场地生命修正恢复

日期：2026-09-13（Asia/Shanghai）。版本：v0.27.0。

## 存档与恢复顺序

FIELD 补充升到 schema 4，增加与场格逐张对齐的 `playerFieldHealthStates`，保存基础生命、有效上限与 HEALTH 修正的 Tag、Amount、limit、Flags。当前生命仍放在既有场格状态中，允许高于基础生命或有效上限。攻击与生命共用原生属性表，因此同时检查跨属性的 FName 标签冲突和合计数量上限。

恢复先按原生顺序重建牌区与场格，再恢复攻击修正、生命修正，最后通过已验证的原生 setter 写入当前生命。生命修正先添加非负值再添加负值，每个原生动作完成后，逐张核对修正表、有效上限及当前生命。正 HEALTH 添加会增加当前生命并按新上限处理这次增加；最终写入必须在其后，否则会改变保存的当前生命。

最终观察窗口继续比较生命状态，只有第一次完成修正重建时写入目标当前生命，后续检查不会把外部变化覆盖掉。报告新增独立 `exactPlayerFieldHealthStatus`。schema 1／2／3 的格式和校验和保持兼容，生命上限覆盖标记为 `legacy-unavailable`。schema 3 已经可能保存衰减结束后的高生命，恢复时也允许这个合法样本超过基础生命。

当前边界要求基础生命和有效上限为正，原生 `+0x120` 独立调整量为零；只接收已验证的 ATTACK／HEALTH 修正和枚举标志，不写入基础生命或独立调整量。玩家其他动态状态的缺口仍需逐层补齐。

## 实机样本

满手牌场景中，同一张苹果同时具有 ATTACK +3 与 HEALTH +3。保存为攻击 5、当前生命／上限 5／5，恢复后牌区真实顺序、场格、攻击、生命和角色资源均通过独立库存比较。

再通过原生动作加入 HEALTH -4，得到当前生命 5、上限 1。新格式保留正负两个生命修正，并按原生动作重建这一状态，没有把当前生命强制压到上限。

HEALTH +3、DECAY 样本恢复后，正常操作使同一张卡的修正依次降为 +2、+1、无修正，有效上限 5→4→3→2，当前生命始终为 5。过程中场上另一张同名苹果保持当前生命／上限 2／2，提供按场格匹配不同实例的样本。

开发构建的干扰测试在最终观察窗口内，只把已知生命加成样本追加为上限 1。请求报告 `011930-600` 准确记录生命检查失败、攻击检查仍通过；随后仅发生一次纯 Route C 回退，报告 `011940-723` 为 `passed / semantic-fallback`。该夹具不会进入正式构建。

格式、校验和、跨属性标签冲突、缺失字段、旧格式兼容和高于上限的当前生命均有纯测试。实机证据与正式构建验收保存在 `QuantumProtoclMod.runtime-evidence/20260913-player-field-health`，以最终 `validation-summary.json` 的 DLL 和报告哈希为准。

正式构建关闭开发夹具，6 组玩家库存比较通过：全新进程正负生命修正、同名双卡与剩余一点衰减、衰减结束、旧 schema 3 高生命、旧 schema 2 满手牌、新 schema 4 无修正。另行恢复原始 schema 1 检查点成功。正式构建中恢复的一点生命衰减，在正常操作后消失，同一卡当前生命仍为 5。DLL SHA-256：`22F754790F3A467D8A48B39FB16BE19D39D71D99EEFB90DA40B339AF5488AF50`。
