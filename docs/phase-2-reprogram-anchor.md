# 第二阶段：“重编程”锚点实验

## 锚点语义

候选检查点在玩家完成“重编程”的局内卡组编辑，并由游戏重建玩家牌区、重新洗牌和抽出五张牌后产生。

读取时不追求保存瞬间的手牌、牌库顺序、玩家场上或墓地。必须使用检查点持久化的完整编辑后卡组与缓存区，随后走原生重编程式的重建、洗牌和五张抽牌。玩家当前生命按保存时数值恢复。

这不是随机结果的逐帧回放，而是一次语义等价的“重编程重开”。详细需求以 [requirements.md](requirements.md) 为准。

## 仍须精确保存和恢复的状态

- 编辑后的完整卡组、每张卡的升级和永久属性。
- 缓存区/储存区的完整构成、升级及必要顺序。
- 玩家保存时的当前生命和其他非卡牌资源。
- 当前流程、关卡、小关、波次和生成倒计时。
- 敌方场上、待处理区和墓地的卡牌，包括标识、升级、位置、生命、回合计数、效果和临时修改。
- 动作队列、胜负判定、游戏结束 UI 与输入状态。

## 已验证的玩家牌区路径

1. `CardEngine:resetPlayerBoard()` 会清空玩家牌库、手牌、缓存区、待处理区、墓地和场上牌。
2. `BP_CardEngine:LoadPlayerCardsStart()` 会加载当前完整牌组、洗牌并抽五张。

两者均未在测试中崩溃，结果符合候选锚点对玩家牌区的语义；但当前活动牌组还只存在游戏进程内，尚未证明能从独立检查点文件恢复完整构成和升级。

## 已失败的敌人重建实验

原 `Ctrl+F1` 在当前战斗中调用 `clearEnemyBoard()`，计划确认清空后再调用 `spawnWaveIndex(savedWave)`。实测清掉最后一个敌人会先触发原生小关完成逻辑，游戏直接进入下一小关。

因此，“在活跃战斗里清空全部敌人再生成旧波次”不能用于恢复，相关热键已经移除。重编程路线若继续，应在全新的战斗上下文中重建敌人，或由 C++ 恢复事务临时抑制过关与自动生成逻辑，并逐字段证明敌人恢复精确。
