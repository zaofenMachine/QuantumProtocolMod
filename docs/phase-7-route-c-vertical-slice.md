# 第七阶段：路线 C 普通小关语义重开

日期：2026-09-03

版本：v0.9.13-dev

状态：核心垂直切片已闭环；同一最终构建连续三轮恢复、程序校验与 UI 验收均通过。

## 闭环结论

路线 C 已证明可以把普通 `DUNGEON` 小关保存到独立文件，并在新的战斗上下文中恢复同一来源关卡和波次。敌人由游戏原生流程生成；玩家活动牌组、缓存区、新掉落物、生命和角色特殊资源槽均恢复正常。保存瞬间的手牌、牌序、玩家场上/墓地、敌人伤势、效果、临时属性和 RNG 仍明确不属于路线 C。

最终验收使用 `cometDungeon1 / CometDungeon1Spawner / waveIndex=1` 的 schema 2 检查点。检查点包含 9 张牌的活动牌组、空缓存区、生命 `9/9`，以及香蕉、苹果、火球术三张尚未使用的“新的掉落物”。v0.9.13 在同一游戏进程内连续恢复三次：三个结构化报告均为 `passed`；第二、第三次均走重复恢复防卡死路径；第三轮由人工进入“重编程”确认三张掉落物 UI 全部存在。特殊资源槽在恢复前和三轮恢复后均为 `0/6`、`isCharacterAbilityOk=True`，没有 UI 错误提示。

最终 DLL SHA-256 为 `601C841D4879A1CC48E7311F7C691A890C09C908870079091666F20F717F9B94`，部署 ID 为 `20260903-011758-412`。最终检查点 SHA-256 为 `D08045C731F0E494B82B49E26E6EC96C9AF6ADF44A54F184DB75C9B2F6143FE6`。运行证据保存在仓库外的 `QuantumProtoclMod.runtime-evidence/20260903-v0913-route-c-final-pass`。

## 当前检查点格式

`route-c.json` 使用 schema 2，保存：

- schema/kind、UTC 时间、游戏 EXE 大小与完整 SHA-256；
- 模式、来源关卡、角色与关卡结构；
- 活动牌组、缓存区、DeckRun 摘要；
- 尚未消费的 `lootDrops`；
- 玩家当前生命、生命上限、波次索引及 Spawner 类/尺寸；
- 规范字段负载校验和。

文件上限为 2 MiB；写入使用同目录临时文件加 Windows 原子替换，并保留上一份 `.bak`。复杂 UE 数组解析支持嵌套结构、字符串和转义字符，且有 1024 项上限。schema 1 会在读取缺失字段前明确拒绝，避免把旧格式误判成损坏的新格式。

## 最终恢复事务

`Ctrl+Shift+F6` 的当前链路为：

1. 校验文件格式、schema、负载校验和、模式、Spawner 和完整游戏 EXE 指纹。
2. 保存可回滚的 GameInstance 语义状态，并导入检查点的角色、关卡、来源关卡、启动牌组和缓存区。
3. 调用 `reloadBattleArea()` 创建全新战斗上下文。
4. 在新 `CardEngine` 的 BeginPlay 前再次导入语义数据，让游戏原生角色初始化创建特殊资源槽。
5. 在目标 SpawnController 的 BeginPlay 前再次导入牌组/缓存，暂时关闭 `autoSpawn`，并把 `currentWaveIndex` 设为目标波次前一项，让游戏自己的延迟启动推进到目标波次。
6. 等待新战斗达到稳定 `OPEN` 且玩家生命初始化完成；清空并逐项恢复 `lootDrops`，随后恢复玩家生命。
7. 校验波次、生命/上限、规范化后的活动牌组、缓存区和新掉落物；恢复 `autoSpawn`，再等待 3 秒稳定窗口后写报告。

第一次恢复可读取当前 GameInstance 牌组作为失败回滚材料。一次恢复通过后，同一进程再次读取相同负载时直接复用已经验证过的检查点语义状态作为回滚基线，不再调用可能卡在旧 `DeckRun` 上的 `getActiveDecklist()`。

## 自动保存与空数组处理

每 750 ms 低频观察 CardEngine 权威引用的 SpawnController。只有 `OPEN` 状态下实例、World 或波次发生变化时，才延迟 1.5 秒捕获一次；也可用 `Ctrl+Shift+F5` 手动保存。

捕获时会把原生流程加入的地牢工具牌规范化，避免重复保存“重编程”和“缓存命中”。UE 4.27 将空 `TArray` Getter 导出为空文本；持久化层规范为 `()`，反射调用遇到该值时保留已经初始化的零长度参数，而不把 `()` 导入成一张默认空白卡。

## 关键失败与修正

- v0.9.0 的复杂 Getter 返回参数未按 FProperty 生命周期初始化，读取触发 `abort`；v0.9.1 统一了参数初始化与逆序析构。
- 原生 Dungeon Spawner 没有蓝图 `_C` 后缀；改为从 CardEngine 的 `mEnemySpawnController` 权威引用取得。
- 具体原生波次 UFunction 钩子不是正常推进的可靠自动保存入口；改为低频读取权威 `currentWaveIndex`。
- 空缓存 `()` 曾被误判为 Getter 失败，之后又曾被导入成空白卡；现已分别在导出和参数导入层规范处理。
- 原生初始化会把地牢工具牌再次加入活动牌组；捕获与校验使用启动牌组规范化，消除了重复卡与连带生命上限变化。
- schema 1 未保存“新的掉落物”；schema 2 加入 `lootDrops`，恢复时清空并逐项重建，Getter 与重编程 UI 均已验证三张卡。
- 同一进程第二次恢复时，旧 CardEngine 的 EndPlay 会在重载前导入之后清空 GameInstance，导致牌组、缓存和生命为空；新 CardEngine/Spawner BeginPlay 的分阶段重放修复了时序。
- 一次实验性 `LoadPlayerCardsStart()` 补救产生 `10/9` 生命与瞬时 UI 错误，已完全移除。
- 特殊资源曾因角色语义数据恢复得晚于 CardEngine 的角色初始化而消失；把第一次重放提前到 CardEngine BeginPlay 前后，恢复前后均稳定为 `0/6 / True`。
- 第三次恢复曾卡在旧运行态的 `getActiveDecklist()`；相同检查点的后续恢复改用最近一次通过验证的进程内基线，最终第二、第三轮均命中该路径并通过。

## 安全边界

- 只接受 EXE 大小 `82718720`、SHA-256 `0DCF220317FA31667C14DD7FB41A6757B94FF7CDE2262E5A87337D00CCB017A6`。
- 只接受普通 `DUNGEON`；拒绝 `DUNGEON_EVENT`、`INFINITE`、教程/Boss 伴生对象及带额外状态的特殊 Spawner。
- 保存要求完整活动战斗、`OPEN`、无活动卡牌提示和可验证的玩家生命。
- 恢复有 90 秒总超时、阶段诊断、失败报告和尽力回滚；恢复事务期间重复热键会被互斥门拒绝。
- 不读取或覆盖游戏原生 `.sav`。
- 自动保存会覆盖唯一检查点；测试旧检查点时必须先保全副本，避免进入第一小关后被正常自动捕获替换。
