# 第三十二阶段：手牌生命修正与场外保存边界

日期：2026-09-20（Asia/Shanghai）。版本：v0.33.0。用户已授权恢复推进，方向继续为“小关重开 + 玩家精确恢复”；重编程重开和敌人精确恢复仍搁置。本阶段实现与最终验收已完成。

## 旧版的真实遗漏

v0.32.0 的普通牌区补充只保存场外 CardInfoInstance 和顺序。实机让奥克塔娃的 INIT 选中一张手牌苹果后，两张同名苹果分别为生命 3/上限 3 和生命 2/上限 2；前者带原生 `mageOctavia_init` HEALTH +1。旧版保存并恢复后，两张都变回 2，修正条目消失，但恢复报告仍为 `passed`、墓地层 `verified`。区域顺序、完整实例和身份集合相等，原生生命及属性表比较为 false，证明旧验证范围漏掉了手牌动态数值。

牌组起点是可丢弃的合成测试设置：将一张春替换为游戏已有定义的奥克塔娃，并固定起手顺序；它不代表用户原牌组自然获得了这张卡，也未改写原生存档或解锁。生命增益则由正常出牌、选择手牌目标、游戏原生技能结算产生，没有直接注入修正。设置记录 `fixture-octavia-setup.json` 与原生效果库存分别归档。旧版失败证据为 `octavia-native-buff-empty-field.json`、`v0320-lost-hand-health.json` 及对应恢复、比较报告。

已有原生移动路径进入 HAND/DECK/TRASH 时会调用 RVA `0xE3E330` 重置动态数值，因此本次选择直接作用于手牌的真实技能作为样本，而非假定场上增益回手后仍保留。

## 保存与恢复契约

新增 `route-c-exact-player-hand-health.json`，使用 HAND HEALTH schema 1，按原生手牌数组下标保存每张卡的基础生命、有效上限和完整 HEALTH 修正条目，包括标签、数量、上限和标志。同名同升级卡分别记录。当前仅覆盖 1–7 张手牌、非负修正、当前生命等于上限；负修正、受伤或超过上限的手牌不在此层范围内。

| 玩家布局 | 新格式 | 保留兼容的旧格式 |
| --- | --- | --- |
| zones | schema 3 | schema 1–2 |
| trash | schema 4 | schema 1–3 |
| field | schema 7 | schema 1–6 |

新格式的非空手牌必须带 16 位十六进制 `playerHandHealthChecksum`，绑定 HAND 补充文件的负载；空手牌必须使用空字符串。HAND 文件同时绑定主 Route C 和完整手牌顺序。文件缺失、损坏、链接错误或手牌不一致时，启动前禁用玩家精确布局、回合和角色充能层，避免再次以默认生命静默恢复。捕获先写 HAND 文件，再发布依赖它的布局。

恢复等最终牌区移动、手牌暂存和场上放置全部完成后，再按手牌位置逐张排入已有原生 HEALTH 动作 RVA `0xE0F640`。新增动作门禁仅允许 HAND、HEALTH、非负数量；同名目标锁定原生 card/state，逐动作核对已完成前缀。最终 3 秒稳定窗口继续核对完整修正和当前生命，发现变化则失败并走已有一次语义回退，不重复补写。

旧布局的读取、写入和负载校验语义保持不变，不要求新 HAND 文件；恢复报告明确标记旧格式的手牌生命覆盖不可用。兼容读取不表示旧检查点已具备新的动态状态覆盖。

## 场外边界与观测

所有新捕获的 zones/trash/field 都统一检查 HAND/DECK/TRASH，已取消“只有生成卡才检查场外属性”的遗漏。核对原生基础攻击、基础生命及等级与游戏卡定义；通过初始化后的反射结构读取升级项，保留省略文本字段的真实默认值。场外攻击修正、计数器、非默认倒计时或 active、独立生命上限调整，以及不支持的修正类型均拒绝精确捕获。DECK/TRASH 仍要求默认生命；只有 HAND 可使用上述 HEALTH 层。符合原门禁时，主 Route C 仍可保存。

F1 在玩家 DECK/HAND/TRASH 控制器新增 `native:cardIdOrder`，值为按原生数组顺序排列的卡牌 ID JSON 字符串数组。比较工具用 ID 在单份库存内部关联完整动态状态，再按原生位置比较；跨进程相等不依赖 GUID 相同。这样两张同名卡交换不同的生命状态不会被多重集合比较掩盖。新检查为 `playerNativeOrderedStateAvailable` 和 `playerNativeOrderedStateEqual`，差异类别为 `player-native-ordered-state`。缺字段、重复或未知 ID、区域错配、覆盖不全均报告 available=false、equal=null，不从元数据排序推断。旧比较项继续保留。

STORAGE/角色能力卡动态状态、效果动作历史、更多生成卡及其它尚未覆盖状态仍不在本次完整恢复承诺内。本阶段没有扩大为任意 HAND 动态恢复，也不表示全游戏精确快照已完成。

## 验证与证据

第一版正式 DLL 关闭开发夹具，SHA-256 为 `4824F87A240FE7AFD1444015BBF1890F217034403A019F912C9369448FF1CA06`，4/4 CTest 通过。已完成的实机验证：

- 普通 zones schema 3、默认 HAND 的恢复及再次保存，玩家比较包含新增原生位置动态状态。
- 原生奥克塔娃技能产生的同名苹果 HAND 3/3 与 2/2，捕获 trash schema 4 后在新进程恢复；再次保存的检查点也恢复通过。
- 带增益的 HAND 苹果与普通 FIELD 苹果共存，field schema 7 恢复通过。
- 恢复后正常把带增益苹果打到 BACK:0，与从同一混合状态直接正常出牌的对照相比，完整玩家检查一致。

比较工具另有 18 项本地契约测试通过。旧实机库存缺新字段时为未知；明确标注的合成夹具验证同名苹果不同 HP 的位置交换、重新生成 GUID 和错误覆盖。合成夹具不计作实机恢复证据。

缺失 HAND 文件的故障曾正确触发 `preflight-route-c` 降级，但暴露出 `std::filesystem::file_size` 异常中的 Windows GBK 文本会令报告不再是有效 UTF-8。实现已改用 `error_code` 和 ASCII 诊断。修正后的正式 DLL 同样关闭开发夹具，SHA-256 为 `2F385429599EAC6808D390A75F9858126CFB360CFC2C3E6CAA1AB954D56347B1`，4/4 CTest 再次通过。

最终 DLL 已再次通过真实增益 HAND 的新进程恢复和再保存恢复。以下三个依赖故障也均正确进入 `preflight-route-c`，未排入 HAND HEALTH 动作、未启动写后失败回退，报告均可按严格 UTF-8 解析：

- HAND 文件缺失，证据 `rejection-final-missing`。
- HAND 文件损坏，证据 `rejection-final-corrupt`。
- 交换两张同名苹果的生命记录，并重新计算 HAND 文件内部校验和，但保留布局原依赖，证据 `rejection-final-wrong-binding`。这验证布局绑定能拒绝内部自洽但已不是原保存负载的文件。

最终构建完成 11 组恢复验收：默认 zones 3、动态 HAND 新进程与再保存、混合 field 7 与再保存，以及旧/新生成卡场地、生成卡空场墓地、全部卡牌在墓地且空手牌。新库存的有序动态状态检查通过；旧库存缺 ID 顺序时仍明确为未知。恢复后正常出牌对照的全部玩家检查一致。敌方状态继续按小关重开，不计为玩家恢复失败。

在 HAND HEALTH 已验证且进入最终稳定窗口后，通过正常 UI 把增益苹果打到场上，恢复正确发现手牌变化，生成一份 `retrying-route-c` 和一份 `semantic-fallback / passed` 报告，且只安排一次回退。未重复补写以掩盖外部变化。

另用游戏已有的“弹幕 + 闪光弹”定义组成可丢弃测试牌组，正常放置闪光弹并由其自身摧毁，触发仍在 HAND 的弹幕 generic counter 由 0 变为 1、special 仍为空。0 计数基线能捕获 zones 3；1 计数状态明确拒绝全部玩家精确布局，主 Route C 仍保存，旧补充均不再链接新主文件。这一真实状态验证了本轮统一门禁，尚未实现其计数恢复。它也是下一切片的直接样本。

最早的 field schema 1 原始检查点另行恢复通过，原始检查点目录所有文件按字节保留。一次旧格式空手牌测试仅因截图时失去焦点中断，实际恢复已通过；重新取得焦点后完成正式回归，保留了中断报告。
