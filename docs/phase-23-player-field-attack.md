# 第二十三阶段：玩家场地攻击修正恢复

日期：2026-09-13（Asia/Shanghai）。版本：v0.24.0。

## 已闭合的缺口

v0.23.0 的库存导出能够观察攻击加成，但旧场地补充不保存它。使用游戏原生属性动作，在原有八张牌中的场上苹果添加普通 +3 后保存并重开，旧玩家检查全部相等，新增攻击统计比较却失败：攻击从 5 丢回 2。本阶段将场地攻击修正接入同一条 Route C 恢复事务。

场地补充升级为 schema 3，新增 `playerFieldAttackStates`，逐张对齐已有行／槽位顺序，保存基础攻击、当前攻击和每条 ATTACK 修正的 Tag、Amount、limit、Flags。记录进入校验和；拒绝不一致的计算结果、不安全标签、大小写等价的重复 FName、超界值和错位记录。schema 1/2 保持原校验算法并继续可读，报告 `exactPlayerFieldAttackStatus=legacy-unavailable`，不将旧存档标成攻击状态已验证。

## 原生恢复路径

在场地位置、生命和行动状态恢复后，先观察所有目标的原生攻击表。重建的基础攻击必须等于保存值，修正表必须为空；不覆盖基础值或清除意外出现的修正。随后通过游戏的 `E0F640` 添加动作逐条重建修正，每条完成后检查所有场地目标。按行／槽位关联卡牌，因此两张相同苹果可具有不同攻击修正。

参数借助反射结构初始化，再用 `DF87C0` 创建原生深拷贝。动作队列消费这份副本和显式保留的目标共享引用；反射参数仍由自身析构管理。没有把存档内容写成运行时指针，没有直接复制稀疏哈希表，也没有调用视觉事件充当属性写入。

每步原生结果必须等于已提交修正的前缀，单步等待上限八秒；最终三秒观察窗口持续复核完整攻击状态。成功报告 `verified-native-attack`。任何异常继续使用已有的一次纯 Route C 回退，报告区分精确失败与语义重开成功。

## 实机证据

临时测试构建使用原生动作在现有苹果上添加 `quantumCheckpointProbe` +3，以及 `quantumCheckpointProbeFlags` +2、Flags=(ONE_ATTACK,DECAY)。清除这两条修正后，库存对比全部相等，包括玩家、敌人和运行时身份，证明该往返未夹带回合或牌区变化。测试热键仅在构建选项开启时存在，正式构建关闭。

- 七张手牌加一张同名场地苹果，新进程恢复两条修正，攻击 7；原有玩家检查和新攻击统计全部相等。
- 恢复后的苹果实际攻击一次，带 ONE_ATTACK 的第二条修正消失，普通 +3 保留，攻击变为 5。继续保存并重开，剩余修正与已行动状态一致。
- 将另一张苹果从手牌放到后排另一槽位，保存的两张同名卡分别为攻击 5 和 2；恢复后分别一致。
- 无修正的 schema 3 场地检查点通过同样比较。
- 在最终观察窗口，通过开发夹具仅清除已知测试修正。请求报告立即以攻击状态不一致失败，随后恰好一次 `semantic-fallback` 通过；未误报精确成功。

开发夹具通过 `Ctrl+Shift+Insert` 添加已知修正、`Ctrl+Shift+F2` 清除它们，均要求唯一场上苹果且拒绝未知修正。只有清除已知测试修正允许在最终观察窗口执行，用于上述负例。默认安装器拒绝包含夹具的 DLL。

构建和两个 CTest 目标通过，覆盖格式边界、标签安全、重复项、计算一致性、校验和与旧格式兼容。正式 DLL SHA-256：`5E92003B926CF2FFCEC28F8B943EAF42719E97AC5B0827621B28D3BEA03D439A`。完整清单、不同构建的哈希、原生调用材料和实机报告在 `QuantumProtoclMod.runtime-evidence/20260913-player-stat-restoration`，最终验收以其 `validation-summary.json` 为准。

## 当前边界与下一项

本阶段新增恢复范围仅为 FIELD 的 ATTACK 修正。DECK/HAND/TRASH 的临时修正、HEALTH/LEVEL 修正、卡牌计数器和额外生成卡仍未闭合。真实春生成的额外苹果仍超出当前活动牌组多重集合约束；本阶段加成恢复样本使用原生动作构造，未编辑检查点载荷。

ONE_ATTACK 的实际消耗已验证，但组合标记随一次攻击整体删除，不能据此声称独立 DECAY 生命周期已通过。下一项继续验证独立衰减、负修正与 limit 的原生行为，再扩展玩家动态状态。重编程重开和敌人精确恢复保持搁置。
