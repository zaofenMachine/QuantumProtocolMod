这是续接方案，没有新增实测结论。当前仍沿“小关重开＋受限玩家恢复”；不更改捕获准入、不扩敌人或重编程。阶段37证明过真实 native busy 后重试，阶段45增加终态回执，阶段46增加只读查看；它们都没有补足 PROCESSING 等待的实机覆盖。

## 最小执行顺序

1. 建立新证据根和独立备份，固定当前 DLL／EXE、原17个 checkpoint、4个 SaveGames、回执及文件集合。旧冻结材料只读，测试结束重新核对并还原原数据。
2. 先在生产构建用正常换波观察自动请求，最多做3次有完整记录的候选；不通过直接写状态、暂停动作、修改期限或另发手动F5来凑正例。来源F1、完整trace、各端点文件哈希和终态回执一起保留。
3. 命中标准必须包含 `capture.processing.waitable`，以及同request/wave的 `auto-capture.processing.retry-scheduled`。随后同请求恢复OPEN并发布，`openWaits>=1`；初始due、原deadline、每次延期和身份必须能对应。只看到动画、后续F1或最终保存成功不够。
4. 如果普通操作未命中或现有日志不能完整绑定deadline，保留“未覆盖”。先设计最小DEV只读见证：在既有请求真实到期且实际处于PROCESSING／无提示时，记录状态、队列、weak身份、request、初始due和原deadline，比较更新器前后文件。它不得写游戏状态、强制暂停、延长期限或造新请求。更改观测后需重新建立源码／DLL绑定；DEV结果不能冒充生产结果。

## 必须区分的分支

| 实际条件 | 当前实现及验收要求 |
| --- | --- |
| PROCESSING，两提示为None，原生队列图合法 | 进入独立等待；即使队列尚未空，也不能记成OPEN native busy |
| OPEN，原生队列图合法但未空 | native busy分支，已有DEV夹具只覆盖这一类 |
| 有提示，未知状态，非法队列图 | 终止拒绝，不作为可重试动画 |
| weak身份／目标生命周期或监听条件变化 | 核对对应拒绝及无后续同请求发布；另设独立负例，不能从一个正例推断全覆盖 |

现有DEV pending夹具明确要求 `busy_retries=1`、`open_waits=0`，因此不能拿它替代PROCESSING正例。依据当前 [捕获和更新器源码](../cpp/QuantumCheckpoint/src/QuantumCheckpointMod.cpp)：PROCESSING判断约5094行，现DEV断言约11923行，保留原请求与500ms延期约12652–12719行；行号仅为续接定位，应重新核对实际代码。

## 通过条件与边界

需要证明同请求、同来源身份和同原deadline；等待前后文件集合／字节无变化，终态只生成一次回执，完成日志与已发布文件／回执绑定一致。重试预算固定为首次due之后30秒，不能每次延期重置。若终止拒绝，保留实际首原因，并分别核对文件与发布轨迹。

文件端点相等不能证明整个区间绝无写入，日志中的 `filesUntouched=true` 也不能替代独立文件观察。PROCESSING单个正例不证明所有生命周期／监听失效分支、实际磁盘故障或恢复正确。需要恢复回归时，应另按当前玩家范围和原25项比较验收，不能使用状态工具的 `matching-files` 作为恢复通过证据。

这一片闭合后，再分别安排监听失效、目标生命周期变化和发布故障；不要把多个未知分支混进同一次失败。
