# 第十五阶段：受限玩家场地、真实抽牌状态与失败回退

日期：2026-09-12。版本：v0.16.0。

本阶段接续 `WIP-current-progress-2026-09-10.md`，修正了“抽牌显示为 0 就代表可以抽牌”的错误判断，并把玩家场地补充接入 Route C。范围仍是普通 DUNGEON 的语义重开加受限玩家状态恢复，不是完整战斗快照。

## 方向复核

保留 Route C 是合理的：关卡重载、原生波次生成和原生创建卡牌已经有运行证据，改用进程内存快照或一次性重建全战场会引入更大的对象生命周期和版本耦合成本。

需要纠正的是精确层之间的关系。独立文件便于版本管理，却不代表状态可以任意组合。场地、墓地和回合状态存在依赖；部分层写入之后失败，也不能靠“跳过该层”恢复原来的小关语义。本阶段改为启动前检查依赖、游戏线程串行执行、统一终验；写入后的失败只允许重新加载一次纯 Route C。

下一阶段应先把恢复计划、原生访问适配和研究探针从大型 Mod 文件逐步分开，保持现有运行验收不变；然后选一个普通敌人、一个字段建立独立验证样本。暂不同时扩大敌方场地、特殊效果和随机数恢复范围。

## 抽牌权威状态

EXE 大小为 `82718720`，SHA-256 为 `0DCF220317FA31667C14DD7FB41A6757B94FF7CDE2262E5A87337D00CCB017A6`。

- UI Getter `0xE323D0` 返回 Deck 状态 `+0x68` 基础倒计时与 `+0x6C` 修正量之和。
- 原生 readiness Getter `0xE11220` 的机器码为 `83 79 68 00 0F 94 C0 C3`，只检查基础倒计时是否为 0。
- ControllerDeck Tick `0xF89010` 经 `0xF8C6C0` 调用该判断，再结合游戏状态更新 `currentCanClickToDraw`，并派发激活事件。

所以 `(base=5, adjustment=-5)` 与 `(base=0, adjustment=0)` 都显示 0，却不具有相同的可操作性。直接写 UI 缓存或调用激活事件无法补足这个差异。

回合补充升级为 schema 2，增加 `playerDrawBase`、`playerDrawAdjustment`，保留显示值和缓存读数用于诊断。保存和读取校验原始两项之和等于显示值。恢复写回两个原始值、全局回合和威胁计数；让游戏自行计算抽牌缓存，不写缓存、不手动派发 UI 事件。

旧 schema 1 仍能解析并验证原校验和，但无法唯一还原原始倒计时。它会在启动前禁用战斗补充，保留 Route C 与有效的未来生成计划。需要在新版中重新保存才能启用这些补充。缺失或损坏的回合文件不能与场地/墓地混用；缺少玩家牌区布局的回合文件同样禁用战斗补充。

有符号整数读取同时修复：原来的通用解析器把负值转换成无符号数做上限检查，错误拒绝合法的负修正量。现在使用 `std::in_range` 检查目标类型范围。

## 玩家场地恢复

独立文件为 `route-c-exact-player-field.json`，与主检查点校验和、EXE、关卡和波次绑定。记录牌库、手牌、墓地、按场格排序的场上卡身份，以及每张卡的格位、当前生命和 `isTurnActive`。

当前门禁包括：玩家墓地及 PENDING 为空，卡牌总集合与活动牌组相符，手牌与场上卡身份无歧义，场上卡限 `naturalApple`、`naturalLemon`、`naturalSpring`，目标格为空，生命不超过原生基础生命。它不承诺任意动态效果、增益、额外计数器或敌方运行状态的精确还原。

恢复过程：

1. 以相同卡牌总集合构造临时 `fixedOrder` Decklist，让游戏原生创建卡牌并抽起始手牌。
2. 暂存校验要求保存的牌库、手牌各自保持相对顺序，全部卡牌身份及升级的多重集合一致。不同水果的临时混排顺序不必等于场格顺序；最终牌区顺序仍严格比较完整 Getter 文本。
3. 逐张把牌库中的目标移入手牌，再通过 `Action_PlayCardToFieldResolve` 放入指定空格。
4. 临时把该卡原生效果数组数量置 0，避免重放已经发生的入场效果；落位后恢复数组，写回生命及攻击状态。
5. 撤销固定牌序，验证最终牌区、场格、生命、攻击状态和回合状态。

两个额外修复来自真实失败样本：

- 自动动作入队后可能滞留。使用公开 `setActionQueueSystemPaused(False)` 调用原生队列驱动 `0xE54510` 推进恢复动作，不伪造手动回合；游戏已经暂停时拒绝覆盖暂停。
- 原生 PlayCard、MoveCard、MoveCardOnField 接口会销毁按值传入的共享指针临时量。调用前补齐临时引用计数，避免每次搬牌窃取一个现存引用。原生调用者 `0xE025B0` 与被调函数释放路径提供了 ABI 证据。

## 执行线程与失败语义

UE4SS 的 Mod `on_update` 在其后台更新线程执行，因此它现在只设置请求标记。实际 UObject、反射与原生操作在 `BP_MousePlayerController_C.ReceiveTick` 后执行，线程 ID 由 BeginPlay 建立并核验，同时阻止重入。恢复开始写玩家状态前还要求连续 750 ms 的 OPEN 观察。

终验窗口持续三秒，按约 100 ms 的节奏重新检查，实际间隔还包括读取成本。验证覆盖当前牌区、场格、生命、攻击状态、角色充能、原始抽牌计数、游戏计算的抽牌缓存、威胁和未来生成计划；任何请求的层未通过，都不能把精确恢复报告为 passed。

临时效果抑制在超时、异常及其他结束路径均执行清理，先核验当前世界和目标卡身份。恢复结果区分：

- `restoreMode=requested`：按预检选定的补充执行；只有所有请求层验证通过才 passed。
- `restoreMode=preflight-route-c`：补充依赖不足，加载前禁用战斗补充，原因在 `fallbackReason`。
- `status=retrying-route-c`：精确恢复失败，准备重新加载。
- `restoreMode=semantic-fallback`：第二次加载只用原 Route C 主检查点。它的 passed 只表示小关语义恢复通过，不表示场地或回合精确恢复通过。第二次失败不会循环重试。
