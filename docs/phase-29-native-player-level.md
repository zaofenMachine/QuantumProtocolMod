# 第二十九阶段：玩家等级来源与 LEVEL 条目

日期：2026-09-13（Asia/Shanghai）。版本：v0.30.0。

## 等级并非属性修正之和

原生 getter `E27CB0` 直接读取卡牌状态 `+0x110`。卡面更新路径 `FB935F` 使用这个 getter，将结果写入卡面 `+0x2A4`。不同于攻击与生命，它没有遍历属性修正表，也没有把 `ECARD_STATS::LEVEL` 的数量加到结果上。

新增只读 `nativeLevel:*`，分别导出原生等级、LEVEL 条目数量及其数量之和，并与 getter 和卡面交叉观测。读取遵守现有 EXE、活动世界、原生所有权、内存布局和数值边界检查。比较工具增加独立 `playerNativeLevelAvailable/Equal`；旧报告缺少覆盖时返回未知。完整标签与标志仍由原有原生属性表比较覆盖，没有用数量之和代替完整表。

## 原生动作验证

开发构建仅在闲置战斗、唯一未修改的场上苹果上，允许排入 LEVEL +3 原生属性动作。普通标签和带 DECAY 的标签分别测试，没有直接写卡牌等级。

- `024526-312` 的苹果等级 1、空属性表；`024534-774` 记录 `quantumLevel, stat=3, amount=3`。同一 GUID，等级及卡面仍为 1，攻击和生命仍为 2，计数器不变。旧完整属性表比较及新增等级条目比较都识别差异。
- 另一同一 GUID `3CCE205C4AD76CBAB3403DA95BEAE4C4` 的 DECAY 条目经历 3→2→1→删除，库存依次为 `024731-234`、`024739-530`、`024829-434`、`024837-715`。变化来自普通攻击和出牌，整个过程原生等级保持 1。
- LEVEL 条目存在时，FIELD 精确捕获明确拒绝不支持的属性类型。保存的主 Route C 仍可用，原有 FIELD 文件不会获得新负载校验和；条目过期后，双苹果场地重新成功保存为 schema 5。

日期均为 20260913。上述结果证明 LEVEL 条目是可存在、可衰减的原生表记录，但不能据其名称推断它会增加当前等级。本阶段保持只读观测和明确边界，没有改变游戏的等级计算规则，也没有宣称已恢复 LEVEL 条目。
