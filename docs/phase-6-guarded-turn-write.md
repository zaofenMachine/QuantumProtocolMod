# 第六阶段：受控回合计数写入与回滚

## 目标

验证活动卡牌的权威回合计数能否像生命值一样跨帧写入、驱动 UI 更新并安全恢复。本阶段仍是可丢弃测试局中的最小探针，不实现完整检查点恢复。

适用范围继续受当前游戏 EXE 指纹约束：文件大小 `82,718,720` 字节，SHA-256 为 `0DCF220317FA31667C14DD7FB41A6757B94FF7CDE2262E5A87337D00CCB017A6`。

## 静态分析

`getCurrentTurnCounter` 的 UFunction thunk 位于 RVA `0x102D130`，其私有实现位于 RVA `0xE323C0`。实现机器码为：

```text
8B 81 98 01 00 00 03 81 94 01 00 00 C3
```

对应逻辑为：

```text
currentTurnCounter = *(state + 0x198) + *(state + 0x194)
```

- `state + 0x198`：基础值。
- `state + 0x194`：运行时调整量。

现有复杂战斗样本中，带可见倒计时的两张 `enemyArtillery` 均为基础值 `0`、调整量 `4`、公开 getter `4`；大部分没有倒计时的玩家牌与敌人则为 `0 + (-1) = -1`。

游戏原生代码也直接修改调整量：重置路径 RVA `0xE3E3B3` 将它设为 `-1`；另一条回合延迟处理路径 RVA `0xE3EF00` 在计算与钳制后写回该字段。没有发现像生命值 RVA `0xE522E0` 那样只执行一次二参数赋值的独立 setter。因此本实验在严格版本和机器码门禁下直接写入调整量，不调用表现层 `Action_*_Visuals`。

## 安全设计

v0.8 的入口为 `Ctrl+Shift+F9`：

- 校验游戏 EXE 大小、公开 getter thunk 地址和私有 getter 的 13 字节机器码。
- 只考虑活动 `BP_InGameCard_C`，并要求状态对象及两个回合字段所在内存页可写。
- 基础值和调整量必须在 `[-1000, 1000]` 内，公开计算结果必须在 `(0, 1000)` 内。
- 选择公开计算结果最大的候选，避开通常为 `-1` 的牌库、手牌等非倒计时卡。
- 写入前调用一次 `getCurrentTurnCounter()`，必须与两个私有字段之和一致。
- 只把调整量加 `1`，保持约一秒；临时值存在期间不调用反射 getter。
- 恢复前重新确认卡牌对象地址、状态指针和内存权限，并要求基础值未变、调整量仍为探针写入值。任何游戏自身的回合推进都会使探针拒绝覆盖。
- 生命与回合探针互斥，防止两个受控写入同时存在。

## 运行结果

- 报告：`turn-write-probe-20260831-130926-149.json`。
- DLL 大小：`500,224` 字节。
- 部署 SHA-256：`6B0168055886214CC6D4BEBCC002B41523D0010D4AADEF5FB79B7371682388DC`。
- 状态：`passed`。
- 写入前基础值 / 调整量 / 计算值 / 公开 getter：`0 / 5 / 5 / 5`。
- 测试调整量 / 计算值：`6 / 6`。
- 请求保持时间：`1000 ms`；实际保持时间：`1004 ms`。
- 恢复前身份复核：通过；基础值 / 调整量 / 计算值仍为 `0 / 6 / 6`。
- 恢复后基础值 / 调整量 / 计算值 / 公开 getter：`0 / 5 / 5 / 5`。
- 用户观察：无崩溃，计数按预期可见地增加并恢复，控制台开始和完成信息正常。

## 结论与边界

当前游戏版本中，活动卡的权威回合计数可以通过精确修改运行时调整量恢复；该写入能够跨帧存在、驱动 UI，同样可以在对象身份和并发变化验证后回滚。生命与回合计数这两项敌方核心数值现已分别完成私有状态、公开 getter 和可视 UI 三层验证。

仍未证明：

- 通用/特殊计数器的显示对象是否持有权威值，还是仅为表现层镜像。
- 持续效果、临时属性修改、自动化与保护状态的权威集合及写回顺序。
- 新建敌方卡牌后，直接写入这些字段是否足以让后续 AI 和动作队列完全接受恢复状态。
- 从菜单重新进入关卡后的对象匹配、暂停事务和失败回滚。

下一阶段优先使用带非零通用/特殊计数器或持续效果的敌人样本，区分显示对象与权威执行状态；不再重复基础生命或回合数值脉冲。
