# 第十七阶段：玩家牌区的真实顺序

日期：2026-09-13（Asia/Shanghai）。版本：v0.18.0。

## 修正的结论

继续用户确定的“小关重开 + 玩家精确恢复”；重编程重开和敌人精确恢复保持搁置。

此前牌库、手牌和墓地保存的是 `getCardInstanceListSorted()`。反汇编确认它先复制原生卡牌数组，再按 `cardSortSetIndex`、`cardSetNumber`、升级和标签排序。这能核验卡牌集合及实例信息，不能证明实际抽牌顺序、手牌左右位置或墓地插入顺序。第九至十六阶段中涉及“牌区顺序”的结论应按这个边界理解。

只读实测进一步证实：把手牌“春”移到两张樱桃左侧，原生数组随屏幕排列变化，排序 Getter 保持不变；正常抽牌移走原生牌库数组最后一张，并追加到原生手牌末尾。

## 实现

- 三个玩家牌区补充升级到 schema 2，保存原生顺序的完整 `CardInfoInstance` 文本。场地数组仍按目的行和格位排列，场地状态与该数组逐项对齐。
- schema 1 继续解析并按原排序 Getter 校验。报告增加 `playerZoneOrderBasis`：`native-array`、`legacy-sorted-only` 或 `unavailable`。旧文件缺失的真实顺序不作推断。
- 只读适配器在游戏线程上读取 CardEngine 原生状态中 HAND `+0x58`、DECK `+0x48`、TRASH `+0x68` 的共享牌区对象。牌区首个 TArray 按 16 字节的共享卡牌引用保存顺序。验证游戏指纹、原生 Getter 和数组复制指令签名、共享所有权、数组范围及每个对象的当前牌区归属后，才导出对应 UObject 的卡牌实例。
- 原生 Getter 线索：HAND `E26300`，DECK `E231A0`，玩家 TRASH `E32320`，数组复制 `E21F10`。未写入这些容器或引用计数。控制器必须连接当前 CardEngine。
- 固定牌序启动保留保存的牌库数组，把手牌反向放到顶部。墓地和场地卡先暂存在中间，再经原生移动及抑制入场效果的出牌流程归位。
- 运行时目标枚举也改用原生顺序。纯计划先保留牌库/手牌的有序子序列，再分配墓地/场地副本；独立墓地恢复复用这套分配逻辑，避免搬走应留在牌库的同名副本。
- 独立墓地的 schema 2 暂存核验考虑末尾抽牌方向：进入起始手牌的额外墓地牌是反序后缀。新旧格式分别核验，最终及三秒稳定窗口都用该格式的真实来源。
- F1 清单保留排序 Getter，并增加 `native:cardOrder`。独立比较工具分别比较原生身份顺序和完整实例文本；旧清单缺少原生数组时返回未知值，不能算作顺序一致。比较前只整理牌区字典的键顺序，牌区内部不排序。

## 后续边界

schema 2 补齐顺序信息，没有扩大支持的玩家动态状态范围。牌库和手牌仍要求非空；场地卡仍限苹果、柠檬和春，PENDING 为空；跨手/场/墓的同身份卡、墓地单卡动态效果及更多玩家计数器仍待逐项实测。下一项继续利用有序对象计划处理这些玩家恢复缺口。
