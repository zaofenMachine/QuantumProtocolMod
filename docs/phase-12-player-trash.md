# 第十二阶段：玩家墓地精确恢复

日期：2026-09-06

版本：v0.14.0-dev

状态：无玩家场上/待处理卡的受限样本中，玩家牌库、手牌和墓地已完成跨进程精确恢复；原生位置迁移、严格 Getter 复核、失败降级、回滚路径和 UI 均已验证。

## 切片边界

本阶段没有直接扩张到完整中途战场，而是在已有固定顺序牌库/手牌层上增加一个独立墓地切片。只有同时满足以下条件才生成 `route-c-exact-player-trash.json`：

- 玩家牌库、手牌和墓地均非空，三者合计不超过 128 张；
- 玩家 `FIELD` 和 `PENDING` 均为空；
- 三个牌区的“标签 + 升级 + 数量”与活动牌组完全一致；
- 手牌与墓地不共享卡牌身份。这个约束避免原生固定抽五张后，无法区分“应保留的手牌副本”和“暂存在手牌的墓地副本”。

补充文件使用独立 schema 1、负载校验和、Route C 校验和链接、游戏 EXE 指纹、关卡名和 wave。文件缺失、损坏、过期或不满足门禁时，只跳过精确墓地层，不阻止 Route C 语义恢复。

## 原生位置迁移证据

游戏 EXE 指纹仍为 SHA-256 `0DCF220317FA31667C14DD7FB41A6757B94FF7CDE2262E5A87337D00CCB017A6`。本阶段确认：

- `AInGameCard + 0x228` 指向卡牌原生状态；其中 `+0x08/+0x10` 是共享对象与控制块，`+0x28` 指向 CardEngine 原生状态；
- `ACardEngine + 0x268` 指向同一原生 CardEngine 状态；
- 完整 `getCardLocation` 包装函数 RVA 为 `0xE27CC0`；
- `Action_MoveCard` 入队函数 RVA 为 `0xE35A10`；
- 位置枚举为 `HAND=0`、`DECK=1`、`TRASH=2`、`FIELD=3`、`PENDING=4`；
- `moveType=DEFAULT(0)` 能修改权威位置，又不会触发销毁或执行卡牌副作用。

首次调用较低层位置映射器时没有保活共享引用，控制块计数下溢并在 RVA `0xE201F7` 访问空共享对象而崩溃。修复后只调用完整包装器，并在每次读取前后验证控制块计数不变。引用修复探针把“缓存命中”从手牌移到墓地再移回手牌，位置、顺序、身份和全部语义状态均恢复，报告为 `passed`。

## 恢复算法

保存时记录三个控制器 `getCardInstanceListSorted()` 的完整有序数组。恢复先把临时固定 Decklist 构造成：

1. 保存牌库；
2. 保存墓地；
3. 反向保存手牌；
4. `fixedOrder=True`。

游戏仍固定抽五张。反射字段 `CardEngine.startingHandSize` 虽可写成 4 并读回，但不会改变该原生抽牌行为，因此不再修改它。真实对照证明，额外抽出的墓地牌会出现在手牌前部，未抽出的墓地前段则与保存牌库形成保序合并。

v0.14.0 据此使用动态规划验证：

- 实时手牌以保存手牌为后缀，前部只能是保存墓地的后缀；
- 实时牌库必须是保存牌库与剩余墓地前缀的保序合并；
- 实时墓地在搬运前必须为空，卡牌总数必须不变。

验证通过后，代码按保存墓地顺序从实时牌库和手牌中选择同一“标签 + 升级”的原生卡对象，依次入队 `DEFAULT` MoveCard 到 `TRASH`。只有牌库、手牌、墓地三个 Getter 的完整文本全部等于存档才标记 `verified`，随后恢复普通活动牌组。超时则把每个已移动对象送回其原 `DECK/HAND` 位置，并要求暂存模型重新成立；无法回滚时整项恢复失败，而不是继续报告成功。
