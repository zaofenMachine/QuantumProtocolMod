# 第五阶段：受控生命值写入与回滚

## 目标

验证第四阶段定位的私有当前生命字段和游戏内部 setter 是否确实可写，同时把实验限制在可自动恢复的最小范围内。本阶段不实现检查点恢复；v0.6.1 验证单次调用内写入与回滚，v0.7 再验证跨帧保持、UI 刷新和延时回滚。

适用游戏版本仍由 [phase-4-native-card-state.md](phase-4-native-card-state.md) 中的 EXE 大小、SHA-256、getter RVA 和机器码签名限定。

## 安全设计

v0.6–v0.7 的写入入口为 `Ctrl+Shift+F12`，并包含以下拒绝条件：

- 游戏主模块必须存在，磁盘文件大小必须等于已验证版本的 `82,718,720` 字节。
- `getCurrentHealth` 的 UFunction thunk 必须位于模块 RVA `0x102D100`。
- 私有 setter RVA `0xE522E0` 的机器码必须精确等于 `89 91 1C 01 00 00 C3`，即只执行 `mov [rcx+0x11c], edx; ret`。
- `AInGameCard + 0x228` 的状态对象及当前生命字段所在内存页必须已提交且可写。
- 目标必须仍存活且已经受伤：`0 < currentHealth < baseHealth <= 10000`。
- 写入前的 `getCurrentHealth()` 必须与私有字段一致，否则拒绝写入。

测试值固定为 `currentHealth + 1`，不会超过已验证的基础生命。v0.6.1 的 RAII 恢复保护会在标准异常路径上重新写回原值；v0.7 在延时恢复前重新枚举并确认原卡对象仍存活、对象地址与状态指针均未变化，而且字段仍等于探针写入值。若游戏已自行改变字段，探针拒绝覆盖。

安装器同时把旧 `QuantumCheckpointProbe` Lua 模组设为禁用，避免其破坏性测试热键与 C++ 探针冲突；卸载时可按部署清单恢复原配置。

## v0.6：失败但未写入的扫描路径

第一次按键被正常捕获，日志停在第一张卡的 `getCardLocation()` 调用：

```text
[QuantumCheckpoint] Read-only call getCardLocation on BP_InGameCard_C ...
```

没有生成 `health-write-probe` 报告，也没有进入 setter。游戏进程没有崩溃，窗口仍被系统判定为可响应，并可正常退出。

该现象说明，即使同一 getter 在批量只读报告中曾成功，仍不应在写入前的安全关键路径中调用不必要的复杂位置逻辑。v0.6.1 因此移除了位置、标签和 GUID getter，不再区分敌我，只选择第一张通过私有状态检查的受伤活动卡。

## v0.6.1：成功结果

- 报告：`health-write-probe-20260830-170627-531.json`
- DLL 大小：`470,016` 字节。
- 部署 SHA-256：`DE43B09134181B90FA82B619C799A1FA69F0B51B81AC3ED0D1317601A058A2F6`。
- 状态：`passed`。
- 目标基础生命：3。
- 写入前私有值 / 公开 getter：`1 / 1`。
- 临时测试值 / 私有读回：`2 / 2`。
- 恢复后私有值 / 公开 getter：`1 / 1`。
- 临时值存在期间没有调用反射 getter；恢复在任何后续反射调用之前完成。
- 用户观察：无崩溃、无卡住、画面生命值无持续变化。

完整日志顺序为：写入前读取公开生命、私有 setter 临时写入并直接读回、私有 setter 恢复、恢复后读取公开生命、写出成功报告。

## v0.7：跨帧保持与可视回滚成功

- 报告：`health-write-probe-20260830-171633-307.json`。
- DLL 大小：`478,720` 字节。
- 部署 SHA-256：`1BF37E35C92390AD0A8C63FB92F34EBCEC57C8A03C5A68CCF948AA8F8008670C`。
- 状态：`passed`。
- 写入前私有值 / 公开 getter：`1 / 1`。
- 测试值 / 写入后私有读回：`2 / 2`。
- 请求保持时间：`1000 ms`；实际保持时间：`1003 ms`。
- 恢复前对象身份与状态指针复核：通过；恢复前私有值仍为 `2`。
- 恢复后私有值 / 公开 getter：`1 / 1`。
- 临时值存在期间仍未调用反射 getter。
- 用户观察：无崩溃、控制台开始/完成信息正常，画面生命值可见地增加并随后恢复。

该结果证明，私有 setter 的写入不仅能在同一次 Mod 调用内读回，也能跨越约一秒的正常游戏帧存活；游戏 UI 会从该权威字段同步刷新，延时恢复后也会再次同步。恢复前的身份和值检查同时验证了最小化“旧对象地址复用”与覆盖游戏自身并发变化风险的保护方案。

## 结论与边界

本阶段证明：在当前游戏版本中，`state + 0x11C` 可由已定位的游戏私有 setter 修改，写入会被同一权威状态对象立即读回、跨帧保留并驱动 UI 更新，也能在重新验证对象身份后可靠恢复原值。这将生命恢复从“权威状态只能读取”的风险降为“可以构造成受保护的持久写回步骤”。

仍未证明：

- 动作队列、死亡判定、治疗上限和后续 AI 是否接受外部写入后的状态。
- 回合计数、计数器、效果与卡牌创建/删除是否有同等安全的写入路径；其中回合计数后来已在[第六阶段](phase-6-guarded-turn-write.md)验证。
- 从菜单重新进入战斗并按依赖顺序恢复完整检查点。

第六阶段已完成回合计数的最小受控写回。后续应在有非零计数器或持续效果的样本中区分权威执行状态与显示状态；同时设计暂停动作队列、验证对象、按依赖顺序写入、失败回滚和恢复 UI/输入的事务边界。
