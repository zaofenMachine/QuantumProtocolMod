## 满手牌来源与恢复顺序

使用明确标记的主档测试牌组：2张基础长弓、4张升级樱桃、7张基础苹果，共13张。它只改变语义启动牌组，不注入 Q2、C3、完整 CardInfo 或卡牌历史。正常游戏启动后，把双弓放入前排0/4；四张樱桃依次打到后排0并执行该排，以正常抽牌得到7张苹果，再将四张樱桃正常送入墓地。实际过程有输入记录、阶段截图和独立 F1；按键命令成功本身不作为游戏效果证明。

构造途中敌人在中间列攻击，玩家生命13→5；双弓保持1/1、未发动且可行动。最终角色充能实际为0/6、许可False。没有使用普通牌库点击、原生搬牌／抽牌写入或许可写入来凑场景。

两次恢复实际各有12个手牌暂存动作：先归还启动手牌，再恢复前6张保存手牌；两张长弓逐张出牌并解除数量抑制、完成空闲边界与场地复核后，才恢复第7张手牌，最后进入资格回放。报告的原生手牌上限7、deferred=true，与完整阶段日志和最终 HAND7 端点相符。中间过程属于运行时断言，不宣称独立连续观察了每帧队列。

现行恢复会先把启动手牌归回牌库，F13 保存手牌又不能包含长弓，因此两个场地目标的初始绑定均为 DECK。HAND／混合起点在该完整流程不可达，不把出牌前必须经过 HAND 的瞬间算成这类覆盖，也不修改守卫制造它。

## 保留的失败与审计修正

第一版13张测试档仍带8点生命上限；原生启动实际产生13点上限，恢复按原守卫拒绝。该失败和主档完整保留，新版本依据原生当前生命及真实截图中的上限13修正主档生命字段，之后启动通过。这是测试档修正，不是产品修复。

首次满手牌审计要求 `verified-position-health` 日志全局唯一，误拒绝了正常的重复复核。实际恢复报告及原25项已经通过，原日志未改。修正后的审计按产品状态机验证全部复核事件：尾牌前两个独立调用点恰两次，完成手牌后及稳定采样阶段分别允许受约束的复核；尾牌排队期间、回放期间、合法窗口之外或非空reason均拒绝。两个实机案例实际计数均为2/2/2。首次审计命令、旧工具字节和错误输出保留，最终四个案例全部使用新工具重新审计。

覆盖合同自测4个正例、35个拒绝变体。自测不是实机次数，也不证明完整 UI 历史。
